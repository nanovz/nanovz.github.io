Requirements for following this page

  1. You have a machine that you can ssh into (a VM, physical machine, cloud server, whatever).
  2. You are using Ansible on Linux or Mac (Windows is more work to install; see the official docs).
  3. You can read.

Introduction

This page is a terse overview of Ansible that gives a basic introduction so you can start experimenting immediately. It defines clear relations between features and provides simple use cases.

Ansible can be confusing at first because there are many ways to do things, but it becomes intuitive. This page is basically a high-level summary of the official Ansible documentation.

What is Ansible

Ansible lets you write predefined configurations for machines and the methods to apply those configurations. Instead of manual configuration of servers (which scales poorly), you automate it. You also obtain a uniform way to describe server configurations for many machines.

Source: Ansible documentation index.

Use YAML or INI formatting?

Use YAML for everything. INI format is acceptable for basic inventories, but YAML is the effective standard for Ansible.

Source: Inventory documentation notes that YAML becomes preferable as the number of managed nodes increases. See Building an inventory.

The most basic project structure

A useful Ansible project requires:

  1. An inventory file (or directory)
  2. A playbook to apply to those inventory groups
  3. Modules to call (built-in and external)
  4. Dealing with secrets. Not dealt with in this page, so go here for vault docs.

Inventory

An inventory defines the hosts and groups that Ansible manages. The preferred format for anything beyond the simplest cases is YAML.

Minimal YAML inventory example: 

all:
  hosts:
    web1:
      ansible_host: 192.0.2.50
    web2:
      ansible_host: 192.0.2.51
  children:
    webservers:
      hosts:
        web1:
        web2:
    dbservers:
      hosts:
        db1:
          ansible_host: 192.0.2.60

Group hosts logically by function (web, db), location, or environment (dev, staging, prod). Avoid spaces, hyphens, or leading numbers in group names. Group names are case-sensitive.

Variables can be defined inline, but the recommended practice is to store them in separate files relative to the inventory: group_vars/ and host_vars/ directories. Prefer not to store variables in the main inventory file itself.

Common connection variables include ansible_user, ansible_ssh_private_key_file, and ansible_port. Never store passwords in plain text.

Sources: Inventory, Building an inventory, Best Practices.

Running ansible playbooks

Use ansible-playbook to execute playbooks. Key flags that affect variable availability and secrets:

  • -i / --inventory: specify inventory file or directory
  • -e / --extra-vars: pass extra variables (key=value or YAML/JSON; use @file for files)
  • --ask-vault-pass or --vault-password-file: supply vault password
  • --vault-id: specify vault identity and password source
  • -l / --limit: limit to a subset of hosts
  • -C / --check: dry-run mode
  • -D / --diff: show differences
  • -b / --become: enable privilege escalation

ansible-playbook -i [inventory]

Minimal example

ansible-playbook -i inventory.yml site.yml

With vault and extra variables: 

ansible-playbook -i inventory.yml --ask-vault-pass -e "env=prod" site.yml

Source: ansible-playbook CLI.

Variables

Variables represent differences between systems. Define them in inventory, playbooks, roles, files, or on the command line. Reference them with Jinja2 syntax: {{ variable_name }}.

Variable names may contain only letters, numbers, and underscores. They cannot begin with a number and cannot be Python or Ansible keywords.

Simple example: 

remote_install_path: /opt/my_app_config

In a playbook or template: 

dest: "{{ remote_install_path }}/foo.cfg"

If a value starts with {{, quote the entire expression for valid YAML.

How variables are referenced between files

Precedence (simplified, from lowest to highest influence in many cases):
role defaults -> inventory group/host vars
-> play vars -> task vars
-> extra-vars (command line).
Full details are in the documentation.

Common placement:

  • Inventory: / group_vars/ / host_vars/
  • Play-level: vars: or vars_files:
  • Role: defaults/ and vars/
  • Registered results from tasks
  • Command-line -e

Inside templates and playbooks you have access to all variables in scope for the current host, plus facts and magic variables.

Sources: Using Variables

Playbooks

A playbook is a YAML file containing one or more plays. Each play maps a set of hosts (from inventory) to a list of tasks. Tasks call modules.

Minimal playbook: 

---
- name: Configure web servers
  hosts: webservers
  become: true
  tasks:
    - name: Ensure nginx is installed
      ansible.builtin.package:
        name: nginx
        state: present

    - name: Start and enable nginx
      ansible.builtin.service:
        name: nginx
        state: started
        enabled: true

Plays can include vars, vars_files, handlers, roles, and conditionals. Use import_* for static inclusion and include_* for dynamic inclusion.
In this case, the task Ensure nginx is installed uses the modules ansible.builtin.package and ansible.builtin.service

Source: Official playbook documentation (linked from the main Ansible docs index).

Templating

Jinja2 templating

Ansible uses Jinja2 for templating. Templates are processed by the template module.

Templating for generating configuration files

Create a template file ending in .j2 (for example nginx.conf.j2). Reference variables with {{ var }}. Conditionals and loops are available inside templates. 

- name: Deploy nginx config
  ansible.builtin.template:
    src: nginx.conf.j2
    dest: /etc/nginx/nginx.conf
    owner: root
    group: root
    mode: '0644'
  notify: reload nginx

Special variables available in templates include ansible_managed, template_host, and others.

Source: template module, and Jinja2 documentation is referenced there.
